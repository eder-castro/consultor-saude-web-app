---
name: Gemini API model lifecycle
description: Provider behavior observed when selecting Gemini models and handling temporary capacity failures.
---

Keep the Gemini model configurable and treat model availability and quotas as provider-managed rather than permanent. Retry transient `429` and `503` responses with short backoff. When the primary model explicitly reports exhausted quota, use a configurable fallback model instead of repeatedly retrying the same exhausted quota. Keep response schemas to the provider-supported subset. Structured responses may take over 30 seconds, so retain a configurable timeout with sufficient headroom.

**Why:** The provider rejected `gemini-2.5-flash` for a new API user and directed new clients to `gemini-3.6-flash`; the newer model then briefly returned a high-demand `503` before succeeding. Later, that model exhausted its model-specific quota while `gemini-3.5-flash` remained available for the same key and successfully processed the same structured image request. The provider also rejected array `minItems` and `maxItems` constraints with a generic `INVALID_ARGUMENT`, while accepting the same nested schema without those constraints.

**How to apply:** When Gemini starts returning model-not-found errors, verify the provider's current recommendation instead of retrying the obsolete model. Preserve the configurable primary and fallback model overrides. Switch to the fallback only for provider responses that explicitly identify quota or rate-limit exhaustion; do not hide credential, payload, or validation errors behind fallback. Preserve transient-capacity retries. If a structured request returns a generic 400, simplify unsupported schema keywords while retaining application-side validation. Keep `GEMINI_TIMEOUT_SECONDS` high enough for structured generation.
