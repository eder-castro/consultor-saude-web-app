---
name: Gemini API model lifecycle
description: Provider behavior observed when selecting Gemini models and handling temporary capacity failures.
---

Keep Gemini models configurable and treat availability and quotas as provider-managed rather than permanent. Use the economical model first and escalate ambiguous visual/document extraction to a configurable power model. If escalation is unavailable, preserve the reviewable economical result. Retry transient `429` and `503` responses with short backoff, but do not repeatedly retry explicitly exhausted quota. Keep response schemas to the provider-supported subset and retain a configurable timeout with sufficient headroom.

**Why:** The provider rejected `gemini-2.5-flash` for a new API user and directed new clients to `gemini-3.6-flash`; the newer model then briefly returned a high-demand `503` before succeeding. Later, that model exhausted its model-specific quota while `gemini-3.5-flash` remained available for the same key and successfully processed the same structured image request. The provider also rejected array `minItems` and `maxItems` constraints with a generic `INVALID_ARGUMENT`, while accepting the same nested schema without those constraints.

**How to apply:** When Gemini starts returning model-not-found errors, verify the provider's current recommendation instead of retrying the obsolete model. Preserve separate economy and power model overrides. Escalate only when the economical extraction flags ambiguity, and never discard its result merely because the power model is unavailable. Do not hide credential, payload, or validation errors behind fallback. Preserve transient-capacity retries. If a structured request returns a generic 400, simplify unsupported schema keywords while retaining application-side validation. Keep `GEMINI_TIMEOUT_SECONDS` high enough for structured generation.
